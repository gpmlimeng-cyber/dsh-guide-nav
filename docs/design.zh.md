# 设计依据：为什么是这个形态

本文记录本插件的设计来源与取舍。它的对照物是 **WorkBuddy 的提示词分级输入链路**，那是一次完整取证（五层链路的实现级细节）后的结论。

---

## 一、对方是什么形态

WorkBuddy 在用户**不知道自己要干什么**时，用五层结构一路把人"喂"到只需要按回车：

```
选应用（腾讯电子签助手）
  → 选模式（合同事项 / 合同签署 / 法律事务 / 诉讼支持）
    → 点胶囊（合同起草 / 合同审查 / 合同对比 …）
      → 输入框自动出现「合同起草 ×」标签
        → 底部推荐「合同起草最佳案例」卡片，点一下整套起手状态都备好
```

取证后的关键事实（与直觉不同的几点）：

| 用户口径 | 代码内真实命名 | 承载 |
|---|---|---|
| Buddy 应用 | `industryBuddy` / `industryTemplate` | 远端目录 + 本地快照 + 授权探活 |
| 模式 | `industryMode` | **`systemPromptAppend` 追加段**，不是独立 agent |
| 快捷入口 | `TemplateScene` | 数据驱动，id 为 `hash(modeId:scene.id)` |
| 提示词输入 | content blocks | 标签是 `scene://<hash>` 的 **resource_link 块**，不是文本 |
| 最佳案例 | **`playbook`** | 远端 discover 流 + 本地封面缓存 |

三个可直接借鉴的机制：

1. **唯一的字符串拼接点是"加法合并"**：`joinPromptAppend(mode, scene)` 把模式段与场景段用两个换行拼起来（上限 16000 字符），且模板里**显式声明"不替代周围指令"** —— 选模式是**加一层视角**，不是换人格；
2. **「换一批」是纯前端分页**，零网络请求；
3. **输入框标签是结构化引用而非文本前缀** —— 带 `sceneId`，删除是"从数组剔除一个块"，且能反查回配置。

---

## 二、为什么不能照抄

WorkBuddy 的五层是**商业产品的商品结构**：每一层都要能被运营在后台配置、被远端下发、被非技术用户理解。

**DSH 不是那个形态。** DSH 的用户是开发者，场景是"我在这个仓库里干活"。

所以本插件的原则是：**保功能，不保结构。**

### 层与层的对应关系

| WorkBuddy 层 | DSH 对应物 | 本插件怎么做 |
|---|---|---|
| ① 应用 | **agent preset** | 已有，不动 |
| ② 模式 | preset 内的 `dsh-persona` | **不做**（见下） |
| ③ 胶囊 | **skill + `/` 斜杠菜单** | **本插件做的部分** |
| ④ 输入标签 | `/skill-name` 字面命令 | ③ 的自然结果，非独立层 |
| ⑤ 最佳案例 | 一组 skill | 未实现 |

**五层塌成三层。**

## 三、四个关键取舍

### 取舍 1：逐级展开（抽屉），不是五层堆叠（货架）

WorkBuddy 把四层**同时可见**铺在屏幕上，因为它的用户不知道自己想要什么，需要层层引导；代价是屏幕上全是入口。

DSH 的可用空间是输入框上方**一行**（`conversation.input.dock`）+ 下方一条（`conversation.composer.dock`）。**所以形态必须从"多行堆叠"改成"一行内分级"**：

```
未选技能：  导航 ┃ [create-miniapp] [contract-review] …
选中技能：  导航 ┃ [create-miniapp] [contract-review] ┃ 已选 contract-review
                                          ↑ 同一行内追加，不新起一行
```

**这不是妥协** —— 在开发者工具里，折叠态只占一行**反而更合适**：不挡路，需要时才展开。

### 取舍 2：不做「模式 / persona」层

直觉做法是"合同事项/诉讼支持做成两个 persona 胶囊"。**三种解释都不可行或多余**：

| 方案 | 做法 | 问题 |
|---|---|---|
| A | 点胶囊 = 换 preset | 会话一有内容即 `agent-preset/locked`，**点一次报错一次** |
| B | 点胶囊 = 往草稿插入强调 | 语义变弱，只影响这一轮 |
| C | 跳过这一层 | ✅ **采用** |

**采用 C 的实质理由**：DSH 的 persona 绑在 agent preset 上，用户**开会话前已经选过身份**。会话开始后再选一次 persona，**语义上是自相矛盾的**（"我选了合同审查 preset，现在又选合同起草 persona"）。

模式差异由 preset 承载，本插件不重复这层。

### 取舍 3：写草稿，不直接发送

用户选中技能后**还要补自己的细节**（"甲方是 A 公司、200 台电脑…"）。

- 写进输入框 = **填空**（把创作降级为填空）
- 直接发送 = **替他决定**

所以点击行为是 `inputActions.insertText('/skill-name ')`，把控制权留给用户。

### 取舍 4：不做场景标签（`scene://`）

WorkBuddy 的标签带 `sceneId`，能反查回一整组配置（plugins + skills + expert）。看起来是个独立机制，**但 DSH 里不需要**：

| | WorkBuddy | DSH |
|---|---|---|
| "一整组东西"的载体 | `sceneId` → 反查远端配置 | **`agent.cordis.yml`**（一个 preset 文件就能挂 subagent、workflow、隔离 realm） |
| 组合在哪选 | **输入框里**，随时换 | **开工前**，选了就锁 |
| 中途能换吗 | ✅ | ❌ `agent-preset/locked` |

**这不是功能缺失，是结构不同**：WorkBuddy 只有一个 agent、没有 preset、没有 workspace 概念，所以必须把所有组合能力塞进输入框；DSH 有 preset，**所以不需要那个中间层**。

DSH 允许的运行时粒度只有一层：

```
preset  → 「我是谁、有什么工具」  开始前选，锁死
/skill  → 「这次用什么方法」       随时可换
```

## 四、真正缺的是什么

抛开五层的商品外壳，用户得到的其实就三件事：

| 用户感知 | 本质 | DSH 载体 |
|---|---|---|
| "它知道我是干这行的" | 一套专业判断标准进了上下文 | **preset 的 persona** |
| "它知道我现在要干嘛" | 一套方法指令进了上下文 | **skill**（`/` 调用） |
| "它知道我的项目背景" | 项目约定进了上下文 | **`AGENTS.md`**（自动） |

**三者都是"把上下文前置"，只是绑在不同的生命周期上。** WorkBuddy 把它们全塞进输入框的选择里；DSH 各自绑在正确的位置，所以不需要中间层。

**结论：DSH 缺的不是机制，是发现层。** 机制（preset / persona / skill / `@` 引用 / mention）全都有，缺的是"让用户知道有什么可用" —— 这正是本插件补的那一格。

---

## 五、与 WorkBuddy 的形态对照

| | WorkBuddy | dsh-guide-nav |
|---|---|---|
| 布局 | 五层同时可见 | 折叠态**只占一行**，逐级展开 |
| 位置 | 占满半屏 | 输入框上方一行 |
| 应用选择 | 自有下拉 | **用官方 preset 选择器**，不重写 Hero |
| 模式层 | 四个 tab | **不做**（由 preset 承载） |
| 卡片视觉 | 带封面图 + 远端流 | 纯文字胶囊（无运营方，不需要好看） |
| 锁定行为 | 随时可换 | 发首条消息后**整条隐藏** |
